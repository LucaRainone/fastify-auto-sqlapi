# 0031. An upsert key under `insertExclude` addresses an existing row — it never names a new one

- **Status**: accepted
- **Date**: 2026-11-17

## Context

Two declarations meet on every generated table that upserts by its primary key:

- `insertExclude: ['id']` — the CLI writes it for every identity/auto-increment PK, and the
  docs say it must be there: the client never picks the key of a new row (ADR 0005);
- `upsertKey: ['id']` — the rows that carry an id update that row, those without one are
  inserted (ADR 0021).

`insertExclude` stripped the field from the client payload before the upsert, the key
included. So every row sent with an id reached the database without one and was inserted
again under a new key: a bulk sync by id silently duplicated every row it meant to update, and
a write join with `upsertKey: ['id']` on a child table generated by the CLI did the same to its
child rows. Nothing failed — unless another unique column of the copy collided, as a 500.

## Decision

**The fields of the upsert key stay on the rows that carry them, and such a key may only name
an existing row.** For a table — or a write join — whose `upsertKey` has a field the target
table lists under `insertExclude`:

- a row **without** the key is a plain insert, the key generated by the database or assigned
  by `beforeInsert` — as before;
- a row whose key the **client sent** updates the row that key names. One `SELECT` per
  statement probes those keys before the upsert; a key naming no row is a **400 `not_found`**
  at its path — `main.<field>`, `<i>.main.<field>` in a bulk, `[<i>.]<section>.<alias>.<j>.<field>`
  for a child row — and nothing of that statement is written;
- a key `beforeInsert` assigned is not probed: the hook names a new row.

A key field outside `insertExclude` is unchanged: the client may still create a row under the
key it sends (ADR 0021).

## Alternatives considered

- **The key wins** — never strip an upsert key field, and let a key naming no row insert one
  under that key. Rejected: it gives the client the choice `insertExclude` exists to deny, and
  on PostgreSQL a client-chosen id is a later collision with the sequence.
- **Refuse the combination in `defineTable`** — rejected: the combination is what the CLI
  generates and what an id-based sync needs; refusing it would push consumers to drop
  `insertExclude` and accept client-chosen ids.
- **Probe inside the upsert statement** (update-only branch) — not expressible as one
  statement on PostgreSQL, where `ON CONFLICT` always inserts on a miss.

## Consequences

- An upsert-by-key on such a table costs one more `SELECT` per statement when rows carry the
  key; none when no row does. On MySQL and MariaDB it precedes the probe the upsert already
  runs (ADR 0021).
- The probe ignores the tenant: a key naming another tenant's row passes it and is refused
  by the tenant conflict guard with a 403, as before.
- In a bulk upsert (not transactional, ADR 0003) the main rows are probed before any is
  written; a child row is probed when its item's children are written, like `missing_key`.
- A new engine code, `not_found`, in the 400 `fields`.
